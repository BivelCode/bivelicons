# Contributing to Bivel Icons

Thank you for considering contributing to **Bivel Icons**!

This document outlines the rules, conventions, and workflows to follow when proposing changes, adding icons, or fixing bugs. Following these guidelines helps us keep the project consistent, predictable, and maintainable.

---

## 📜 Code of Conduct

This project adheres to the [Contributor Covenant Code of Conduct](https://www.contributor-covenant.org/version/2/1/code_of_conduct/).

By participating, you are expected to uphold this code.

Please report unacceptable behaviour to [bivelcode@gmail.com](mailto:bivelcode@gmail.com).

---

## 🛠️ Development Setup

### Prerequisites

- [Node.js](https://nodejs.org/) **v24 LTS** or later
- [pnpm](https://pnpm.io/) **v11** or later
- [Git](https://git-scm.com/)

### Getting Started

1. **Fork** the repository and clone it locally.
2. Install dependencies:

```bash
pnpm install
```

3. Run a full build to verify that everything works:

```bash
pnpm build
```

This executes the complete pipeline:

```text
assign unicodes → lint → optimise → generate fonts
```

The first run can take a while because it processes all SVG files. Subsequent builds should be faster thanks to Turborepo caching.

## 🧱 Project Architecture

A detailed description of the repository structure and files can be found in the main `README.md`.

Here is a quick overview of the most important areas for contributors:

| Area                       | Description                                                                                    |
| -------------------------- | ---------------------------------------------------------------------------------------------- |
| `src/icons/`               | Original SVG files — the single source of truth for icons.                                     |
| `configs/styles.config.js` | Registry of all icon styles, including prefixes, font names, and Unicode allocation.           |
| `configs/codepoints/`      | Permanent mapping between icon names and Unicode codepoints.                                   |
| `scripts/`                 | Build pipeline scripts for assigning codepoints, validating, optimising, and generating fonts. |
| `packages/webfonts/`       | Generated npm package. **Do not edit manually.**                                               |

> **Important:** Files generated by the build pipeline must never be manually modified. Changes should always be made to the source files or configuration that generates them.

## 🎨 Adding a New Icon

### 1. Prepare the SVG

Place the SVG file inside the appropriate style directory:

```text
src/icons/<style>/
```

The SVG filename must follow these rules:

- Use **lowercase kebab-case**.
- Example: `arrow-right.svg`
- Example: `cloud-upload.svg`
- Include a valid `viewBox`, for example:

```xml
viewBox="0 0 24 24"
```

- Use **fill colours only**.
- Do not use strokes.
- Include at least one visible drawable element such as:
  - `<path>`
  - `<rect>`
  - `<circle>`
  - `<polygon>`
  - `<g>`
- Do not use inline JavaScript.
- Do not reference external images.
- Avoid unsupported or unnecessarily complex SVG filters.

Example:

```text
src/icons/solid-rounded/arrow-right.svg
```

### 2. Run the Build Pipeline

Run:

```bash
pnpm build
```

The pipeline will:

1. Assign a permanent Unicode codepoint to the new icon.
2. Validate the SVG structure.
3. Optimise and normalise the SVG using SVGO.
4. Generate the webfonts and CSS files.
5. Update the generated package.

### 3. Verify the Result

Open the generated `index.html` test page and verify that the icon appears correctly.

The generated CSS class follows the project's naming convention:

```text
.bi-{prefix}-{icon-name}
```

For example:

```html
<i class="bc bi-sr-arrow-right"></i>
```

> The exact prefix depends on the registered icon style.

### 4. Create a Changeset

Every pull request that adds, changes, or removes icons must include a Changeset.

Run:

```bash
pnpm changeset
```

Select the package or packages affected by the change.

Use:

- **minor** for new icons or new functionality;
- **patch** for icon corrections or bug fixes.

Write a clear summary describing the change.

Example:

```text
[webfonts] Add "arrow-right" icon to Solid Rounded style
```

Commit the generated Changeset file together with the corresponding source changes.

## 🎭 Adding a New Icon Style

Adding a new style requires registering it in the project's style configuration.

### 1. Create the Source Directory

Create the corresponding icon directory:

```text
src/icons/<new-style>/
```

Add the SVG files for the new style.

### 2. Register the Style

Add a new entry to:

```text
configs/styles.config.js
```

Example:

```js
{
  id: 'new-style',
  prefix: 'bi-ns',
  fontName: 'bivelicons-new-style',
  inputDir: srcDir('new-style'),
  unicodeStart: 0xe000,
}
```

The exact Unicode allocation must follow the project's current Unicode allocation strategy.

### 3. Build the Project

Run:

```bash
pnpm build
```

The build pipeline should generate the corresponding:

- webfont;
- CSS file;
- codepoint mapping;
- package artifacts.

### 4. Add a Changeset

A new icon style is a **minor** change.

Create a Changeset:

```bash
pnpm changeset
```

Then open a pull request following the contribution requirements below.

## 🔄 Build Pipeline Overview

The project uses a multi-step build pipeline:

```text
src/icons/
    │
    ▼
assign-unicodes.js
    │
    ├── validates icon names
    └── allocates immutable codepoints
    │
    ▼
lint-svg.js
    │
    ├── validates XML
    ├── validates viewBox
    ├── validates drawable elements
    └── validates fill-only SVGs
    │
    ▼
optimize-svg.js
    │
    └── SVGO optimisation and normalisation
    │
    ▼
build-fonts.js
    │
    ├── Fantasticon webfont generation
    ├── CSS generation
    └── package generation
    │
    ▼
packages/webfonts/
    │
    └── npm-ready package
```

All required steps are executed through:

```bash
pnpm build
```

Turborepo is responsible for task orchestration and caching.

Only affected tasks should be reprocessed when caching is available.

The pipeline follows a **fail-fast** approach: if a required step fails, the build stops.

## ✅ Pull Request Checklist

Before opening a pull request, verify:

- [ ] My SVG files follow the naming conventions.
- [ ] My SVG files follow the project's design and technical rules.
- [ ] I added a Changeset with `pnpm changeset`.
- [ ] I ran `pnpm build` locally and it succeeded.
- [ ] I verified the icons in the test/preview page.
- [ ] I did not manually edit generated files.
- [ ] I did not modify files inside `packages/webfonts/` manually.
- [ ] My commits follow the Conventional Commits format.
- [ ] I updated documentation if the change requires it.
- [ ] I added or updated tests when applicable.

## 📝 Commit Conventions

The project uses **Conventional Commits** to maintain a clean and consistent Git history.

Common prefixes:

| Prefix      | Usage                                        |
| ----------- | -------------------------------------------- |
| `feat:`     | New icon(s), new style, or new functionality |
| `fix:`      | Icon corrections or bug fixes                |
| `docs:`     | Documentation updates                        |
| `chore:`    | Tooling, dependencies, or maintenance        |
| `refactor:` | Code changes without changing functionality  |
| `build:`    | Build system or package changes              |
| `ci:`       | CI/CD configuration                          |
| `test:`     | Adding or updating tests                     |
| `style:`    | Formatting-only changes                      |

### Examples

```text
feat(icons): add arrow-right to solid rounded style
```

```text
fix(icons): correct viewBox on cloud-upload
```

```text
docs(contributing): update SVG design rules
```

```text
build(turbo): configure icon build pipeline
```

Commit messages should be:

- concise;
- written in English;
- descriptive;
- consistent with Conventional Commits;
- focused on a single logical change.

## 🧪 Testing & CI

Every pull request triggers the CI workflow:

```text
.github/workflows/ci.yml
```

The CI pipeline runs the project's required validation steps, including the build.

A pull request must not be merged if the CI pipeline fails.

Before pushing changes, contributors should run the same validation locally whenever possible:

```bash
pnpm ci
```

If the repository does not currently define a `ci` script, use the project's documented validation commands instead.

## 🚀 Release Process

Releases are managed using **Changesets** and the repository's release workflow.

The general workflow is:

```text
Pull Request
     │
     ▼
Changeset added
     │
     ▼
Pull Request merged
     │
     ▼
Changesets Version Packages
     │
     ▼
Version + CHANGELOG generated
     │
     ▼
Release workflow
     │
     ▼
npm publish
```

When a pull request containing a Changeset is merged, Changesets prepares the versioning information.

The generated versioning changes are reviewed before the release is published.

The release workflow then publishes the new package version to npm and updates the changelog.

Maintainers are responsible for reviewing and approving the generated release changes before publication.
